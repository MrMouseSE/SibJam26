# SKILL: Сбор PROJECT_CONTEXT.md через интервью с пользователем

## 1) Назначение

Этот skill нужен, чтобы собрать контекст проекта через диалог с пользователем и сформировать итоговый документ уровня `PROJECT_CONTEXT.md`.

Цель: после серии вопросов и ответов получить структурированный, актуальный, пригодный для повторного использования документ по конкретному проекту.

## 2) Результат

На выходе должен быть файл `PROJECT_CONTEXT.md`, включающий:

1. Краткое описание проекта.
2. Структуру репозитория (важные папки/файлы).
3. Технологический стек и зависимости.
4. Точки входа и жизненный цикл.
5. Сцены/экраны/роутинг и переключение.
6. Архитектурный паттерн модулей.
7. Ключевые подсистемы.
8. Где хранятся данные проекта.
9. Риски/технические наблюдения.
10. Как использовать документ в работе.
11. Когда и как обновлять документ.

## 3) Принципы интервью

1. Идти от общего к частному.
2. Не задавать открытые абстрактные вопросы без контекста.
3. Каждый вопрос должен вести к конкретному разделу итогового документа.
4. Если пользователь не знает ответ, фиксировать это явно как `TBD`.
5. После каждого блока вопросов делать короткое резюме и подтверждать понимание.
6. Не блокироваться на идеальной полноте: сначала черновик, потом уточнения.

## 4) Пошаговый процесс

### Шаг 0. Инициализация

Сразу сообщить пользователю цель:

- “Я задам серию коротких вопросов и соберу из ответов полноценный `PROJECT_CONTEXT.md`.”

### Шаг 1. Паспорт проекта

Собрать:

- название проекта;
- тип проекта (игра, сервис, веб, мобильный, tool и т.д.);
- целевая платформа;
- текущий статус (MVP, production, prototype).

### Шаг 2. Технологии и зависимости

Собрать:

- основной стек/движок/язык;
- ключевые внешние библиотеки и пакеты;
- система сборки/запуска;
- окружения (dev/stage/prod), если применимо.

### Шаг 3. Структура репозитория

Собрать:

- какие папки критичны;
- где лежит основной код;
- где лежат данные, ассеты, конфиги, тесты;
- какие файлы считаются “точками входа”.

### Шаг 4. Архитектура и модули

Собрать:

- основной архитектурный паттерн;
- ключевые слои (например: system/mechanic/component/container);
- как устроены зависимости между слоями;
- правила добавления новой фичи.

### Шаг 5. Runtime flow / жизненный цикл

Собрать:

- как приложение стартует;
- кто инициализирует подсистемы;
- как идет главный цикл обновления/обработки;
- как происходит завершение/очистка.

### Шаг 6. Состояния/роутинг/сценарии

Собрать:

- список состояний (или экранов/роутов);
- типовой порядок переходов;
- кто управляет переходами;
- как добавляется новый state/route.

### Шаг 7. Данные проекта

Собрать:

- где хранятся игровые/бизнес-данные;
- формат данных (ScriptableObject, JSON, DB, YAML и т.д.);
- где лежат настройки и баланс;
- правила изменения данных.

### Шаг 8. Ограничения и правила

Собрать:

- обязательные архитектурные правила;
- запреты/антипаттерны;
- требования к созданию сущностей (например, только через фабрики).

### Шаг 9. Риски и технический долг

Собрать:

- известные риски;
- нестабильные зоны;
- устаревшие конфиги/точки рассинхрона;
- приоритеты на ближайшие улучшения.

### Шаг 10. Процесс актуализации документа

Собрать:

- когда обновлять `PROJECT_CONTEXT.md`;
- кто ответственен;
- минимальный checklist обновления.

## 5) Набор стандартных вопросов (готовый скрипт)

Ниже шаблон вопросов, которые нужно задавать пользователю.  
Вопросы задаются блоками, по 3-6 за раз.

### Блок A: Общий контекст

1. Как называется проект и какая его основная цель?
2. На каких платформах проект должен работать?
3. Это прототип, активная разработка или уже production?

### Блок B: Технологии

1. Какой основной стек/движок/язык?
2. Какие библиотеки/пакеты критичны для проекта?
3. Как запускается и собирается проект локально?

### Блок C: Структура

1. Какие папки в репозитории считаются ключевыми?
2. Где лежит основной код?
3. Где лежат данные/ассеты/конфиги?

### Блок D: Архитектура

1. Какой основной паттерн архитектуры используете?
2. Какие роли у основных сущностей (например System/Mechanic/Component/Container)?
3. Какие правила обязательны при добавлении новой фичи?

### Блок E: Flow

1. Какая точка входа приложения?
2. Как устроен цикл обновления/обработки?
3. Какие состояния/этапы проходит приложение в типовом сценарии?

### Блок F: Расширение

1. Как правильно добавить новую фичу (шаги)?
2. Как правильно добавить новый state/route?
3. Какие проверки обязательны перед завершением задачи?

### Блок G: Риски

1. Какие известные технические риски уже есть?
2. Какие места чаще всего ломаются при изменениях?
3. Что обязательно нельзя делать в этом проекте?

## 6) Правила уточнения

Если ответ неполный:

1. Задать 1 уточняющий вопрос с вариантами.
2. Если всё равно нет данных — пометить `TBD`.
3. Не останавливать сбор документа из-за одного пробела.

Если ответы противоречат друг другу:

1. Явно указать конфликт.
2. Попросить выбрать один вариант.
3. Зафиксировать выбор как окончательный в документе.

## 7) Шаблон итогового документа

После интервью собрать `PROJECT_CONTEXT.md` по этому шаблону:

1. `Кратко о проекте`
2. `Структура репозитория (важное)`
3. `Зависимости и техстек`
4. `Точки входа и жизненный цикл`
5. `Сцены/экраны/роутинг и переключение`
6. `Архитектурный паттерн`
7. `Ключевые подсистемы`
8. `Где искать данные`
9. `Важные наблюдения и риски`
10. `Как использовать этот файл в работе`
11. `Когда обновлять этот файл`

## 8) Критерии качества готового PROJECT_CONTEXT.md

Документ считается готовым, если:

1. Читатель без знания проекта понимает, где что лежит и как это запускается.
2. Понятно, где править код под конкретный тип задачи.
3. Есть список архитектурных правил и запретов.
4. Есть явная последовательность стейтов/роутов и способ ее расширения.
5. Есть список рисков и триггеры обновления документа.

## 9) Definition of Done для этого skill

1. Проведено интервью по блокам A-G.
2. Собрано и согласовано резюме с пользователем.
3. Создан/обновлен `PROJECT_CONTEXT.md`.
4. В документе нет пустых критических секций (допустимы только пометки `TBD`).
5. Пользователь подтверждает, что документ отражает проект.
